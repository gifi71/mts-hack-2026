# 0003. Ansible до CNI и Argo CD, дальше GitOps

## Контекст

Платформа состоит из десятка компонентов с зависимостями: CRD до ресурсов, cert-manager до сертификатов,
Prometheus Operator до ServiceMonitor. Повторный запуск не должен ломать состояние.

## Решение

- **Ansible** делает то, без чего нет кластера: ОС, containerd, kubeadm, Calico (подам нужна сеть до Argo CD),
  Helm, Argo CD и root Application.
- **Argo CD** синхронизирует `gitops/apps`: Helm-чарт с Application на каждый компонент. Порядок задают
  sync-waves, health дочерних Application включён в `argocd-cm`, поэтому волна ждёт готовности предыдущей.
- Values Argo CD лежат в `gitops/platform/argocd` и используются Ansible.
- Ansible ждёт `Synced/Healthy` всех Application, поэтому `make deploy` завершается рабочей платформой.

## Варианты

- **helmfile**: проще и детерминированнее, но без self-heal и без истории изменений в кластере.
- **Только Ansible + Helm**: каждое изменение требует прогона плейбука, дрейф не исправляется.
- **Отдельный репозиторий для GitOps**: нужен, когда CI приложения обновляет теги образов.
  Здесь приложение не собирается, достаточно одного репозитория.

## Последствия

- Self-heal: ручные правки в кластере откатываются к состоянию из git.
- Найдены и исправлены две особенности Argo CD 3.x:
  - чарт по умолчанию игнорирует обновления `/status`, из-за этого health замерзал и волны не продвигались;
  - клиентский diff не знает дефолтов CRD Gateway API и показывал вечный OutOfSync.

  Включены обработка статусов и server-side diff.
- Узлу нужен доступ к GitHub. Ревизия задаётся переменной `gitops_revision`, CI проверяет конкретный коммит.
